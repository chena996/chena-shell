# Chena-Shell 功能梳理与改进优化建议书

> 版本：v1.0（基于当前代码基线静态分析）
> 日期：2026-11-19
> 说明：本文档**仅通过阅读源码**得出，未运行程序、未修改任何代码。所有结论均标注了代码位置，便于核对。
> 代码范围：`src/`（React 前端）、`src-tauri/src/`（Rust 后端）、`tauri.conf.json`、`capabilities/`。

## 一、总体判断

Chena-Shell 目前已经具备一个「可日常使用」的 SSH 终端雏形，核心链路（连接 → 交互终端 → 监控 → 端口转发 → SFTP → 加密配置）是通的，且在若干细节上做了超出同类玩具项目的处理（退出码兜底、配置加密、AI attach 令牌、日志归档）。

但从代码看，当前处于「功能点密集堆叠、架构尚未收敛」的阶段，主要矛盾有三个：

1. **协议层过度依赖 `exec` + 文本解析**：SFTP、监控、端口转发都挂在同一条 SSH 连接的命令通道上，性能和鲁棒性都有明显天花板。
2. **MCP 服务不完整**：这是产品最大卖点（"AI 友好"），但当前实现不满足 MCP 协议，主流 AI 客户端基本无法接入。
3. **状态模型存在结构性隐患**：`SessionHandle` 的 `Clone` 语义与 `Arc::make_mut` 组合，会让"修改配置"这一常见操作把会话对象整体换掉，导致连接状态错乱。

以下按「功能梳理 → 问题清单 → 改进建议 → 路线图」展开。

## 三、关键问题清单

> 优先级定义：
> **P0** = 会造成数据/连接错误或核心卖点不可用；**P1** = 功能缺失或明显体验问题；**P2** = 代码质量与长期维护。

### 3.1 P0｜修改会话配置会把整条会话对象替换掉

**位置**：[commands.rs#L881-L894](../src-tauri/src/commands.rs#L881-L894)、[commands.rs#L174-L187](../src-tauri/src/commands.rs#L174-L187)、[session.rs#L395-L408](../src-tauri/src/session.rs#L395-L408)

`Arc::make_mut(entry.value_mut())` 的作用是：**当强引用计数 > 1 时，克隆出一份新的 `SessionHandle` 并替换 map 中的 Arc**。而 `SessionHandle` 的 `Clone` 实现里：

```rust
connected: AtomicBool::new(self.connected.load(Ordering::Relaxed)),
io_tx: Mutex::new(self.io_tx.lock().clone()),
```

这是**值拷贝**，不是共享。而连接线程在 `connect()` 里持有 `me: Arc<Self>`（[session.rs#L461](../src-tauri/src/session.rs#L461)），监控线程与 `exec()` 也会 clone Arc，因此 refcount 经常 > 1。

**后果**：用户在会话已连接时编辑名称/分组、或新增一条端口转发 → map 里的 Arc 被换成"快照副本"，副本持有旧的 `io_tx` 与 `connected=true`，而真正在跑的事件循环仍在更新**旧对象**。表现为：连接状态显示正常但输入无响应、断开失败、监控不再更新。这类问题偶发且极难复现。

**建议**：
- `SessionHandle` 内部可变状态全部改为 `Arc<Inner>` 共享（`connected: Arc<AtomicBool>`、`io_tx: Arc<Mutex<...>>`），使 `Clone` 变为浅拷贝语义；
- 或更彻底：`config` 单独放到 `Arc<RwLock<SessionConfig>>`，业务代码只改 config，不碰 handle；
- 短期最小改动：`mutate_config` 改为 `inner.sessions.get(sid)` 取 Arc，再用 `Arc<RwLock<...>>` 包 config 做原地修改，禁止对 `SessionHandle` 做 `make_mut`。

### 3.2 P0｜MCP 服务不符合协议，AI 实际接不进来

**位置**：[mcp_server.rs#L69-L98](../src-tauri/src/mcp_server.rs#L69-L98)

问题点：

1. **每条 TCP 连接只处理一个请求**（`read` 一次、`dispatch` 一次、`shutdown`），而 MCP 客户端预期长连接、多请求、`initialize` 握手。
2. **缺少 `initialize` / `notifications/initialized` / `resources/list` / `prompts/list`**，任何客户端第一步握手就 `method not found`。
3. **不是 HTTP/SSE 传输**，也没有做 stdio 适配，客户端无法按标准方式连接。
4. **无鉴权**：`session_attach` 只要传 `session_id` 就发令牌（[mcp_server.rs#L370-L385](../src-tauri/src/mcp_server.rs#L370-L385)），任何本机进程都能拿到控制权。
5. `session_exec` 的 `timeout_ms` 参数在 schema 中声明了但**代码里完全没用**（固定 30s，见 [session.rs#L539](../src-tauri/src/session.rs#L539)）。
6. `WaitConfirm` 分支只返回 `WAIT_CONFIRM`，但 UI 里没有对应的确认入口 → AI 侧永远等不到结果。

**建议**（按投入排序）：
1. 补 `initialize`（返回 `protocolVersion`/`capabilities`/`serverInfo`）、`notifications/initialized`（空响应）、`ping` 已有；
2. 传输层改为 **Streamable HTTP**（单端点 POST + `Accept: text/event-stream`），或直接提供 **stdio** 模式（`main` 启动参数 `--mcp-stdio`），后者实现成本最低且兼容性最好；
3. `session_attach` 增加人工确认：弹窗"AI [客户端名] 请求接入 [会话名]，原因：xxx"，用户点同意才发令牌；同时把令牌有效期（如 30 分钟）与来源 IP/进程记录到 AI 活动时间线；
4. `timeout_ms` 透传到 `IoCmd::Exec`；
5. 补充 `sftp_*` 相关 MCP 工具（读目录、读文件、写文件）——这是 AI 场景下最实用的能力缺口；
6. `WaitConfirm` 落地为"待确认"队列 + UI 弹窗，用户批准后异步继续执行。

### 3.3 P0｜主机密钥永不校验

**位置**：[session.rs#L65-L81](../src-tauri/src/session.rs#L65-L81)

```rust
async fn check_server_key(...) -> Result<bool, Self::Error> {
    ...
    Ok(true)   // 永远接受
}
```

指纹只写进日志，不参与判断。**这是可被中间人攻击的**，对一个"运维工具"来说是硬伤。

**建议**：实现 TOFU（首次使用即信任）——指纹落到 `%APPDATA%\chena-shell\known_hosts`，二次连接比对，不一致时弹"主机密钥已变更"高危提示（红色、需手动确认）。russh 已在 handler 中给出算法与 SHA256 指纹，实现成本不高。

### 3.5 P1｜终端日志默认开启且明文落盘

**位置**：[state.rs#L29-L32](../src-tauri/src/state.rs#L29-L32)、[logging.rs#L189-L208](../src-tauri/src/logging.rs#L189-L208)

`log_enabled` 默认 `true`，会把 **shell 全部输出**追加到 `%APPDATA%\chena-shell\logs\sessions\*.log`，包括：

- `sudo` 的提权过程与报错；
- 用户手动 `cat` 出来的密钥/证书/`.env`；
- 部分场景下的密码回显。

这些文件是**明文**，且没有任何脱敏或权限收紧。对一个内部运维工具，这是比"配置文件加密"更现实的数据泄漏面。

**建议**：
1. 默认改为**关闭**，首次开启时给出说明；
2. 提供敏感词脱敏（`password`、`passwd`、`token`、`PRIVATE KEY`、`AWS_SECRET` 等命中后替换为 `***`）；
3. 提供保留天数（如 7 天）自动清理；
4. 可选：日志用同一套 AES-GCM 密钥加密，或仅在用户显式"导出"时明文落地。

### 3.6 P1｜SFTP 性能与鲁棒性受限于 `exec` + `base64`

**位置**：[commands.rs#L362-L418](../src-tauri/src/commands.rs#L362-L418)、[commands.rs#L421-L462](../src-tauri/src/commands.rs#L421-L462)

当前实现的问题：

| 现象 | 原因 | 量化 |
|---|---|---|
| 上传大文件极慢 | 每 4000 字符 base64 一次 `ssh exec` | 10MB 文件 ≈ 3500 次往返 |
| 下载大文件内存膨胀 | `base64` 全量输出进内存再解码 | 10MB 文件峰值 ~27MB |
| 传输中终端卡顿 | `IoCmd::Exec` 在事件循环里 `await` 完成才返回 | 阻塞终端 I/O |
| 中途失败留残file | 首块 `>` 后续 `>>`，无事务 | 远程留半截文件 |
| 进度条不准 | `bytes = base64_len * 3 / 4` 估算 | 与实际有偏差 |
| 目录列表在非 GNU 环境为空 | `find -printf` 失败后回退 `ls -la`，但解析器仍按 `|` 分割 | BusyBox/macOS 下**声称有目录但显示为空** |

**建议**：
1. **引入 `russh-sftp`**（或 `openssh-sftp-client`），用真正的 SFTP 子系统做 list/read/write/remove/rename/mkdir/stat，一次性解决上述所有问题，且天然支持断点续传（`seek`）与权限位；
2. 若短期不上 SFTP 协议，至少：
   - 分块改为写临时文件 `path.part`，成功后 `mv` 原子替换；
   - 块大小动态调整（如 32KB），减少往返；
   - `Exec` 从事件循环中移出，改为每次 `exec` 独立 `tokio::spawn`（用新的 channel）；
   - 补 `ls -la` 的解析分支，或统一用 `find -maxdepth 1 -exec stat` 输出稳定格式。

### 3.7 P1｜监控采样串行阻塞、周期漂移

**位置**：[monitor.rs#L50-L82](../src-tauri/src/monitor.rs#L50-L82)

```rust
std::thread::spawn(move || loop {
    std::thread::sleep(Duration::from_secs(interval_secs));
    collect(&state);   // 内部逐会话串行 recv_timeout(8s)
});
```

- 单线程 + 逐会话串行：3 个会话时，一轮最坏 24 秒，UI 上仍是"1 秒刷新"的假象；
- 采样命令与 SFTP/转发共用同一 SSH 连接，大文件传输时采样必然超时；
- 首轮没有基线（`prev.cpu_total == 0` / `prev.at == None`），CPU 与网络第一帧恒为 0；
- 文件头注释仍写"每 2 秒一次"（[monitor.rs#L1](../src-tauri/src/monitor.rs#L1)），与 `run_loop(state, 1)` 不一致。

**建议**：
1. 每会话一个独立采样线程（或 `tokio::spawn`），间隔自适应（连接空闲 1s，传输中 5s）；
2. 采样改用**独立 SSH 连接**，避免与终端/传输争抢；
3. 首轮采样只做基线不回传；
4. 增加"上次成功时间"，UI 上对超过 3 个周期未更新的会话显示"数据陈旧"角标。

### 3.8 P1｜`read_log` 可能在 UTF-8 边界处 panic

**位置**：[logging.rs#L240-L257](../src-tauri/src/logging.rs#L240-L257)

```rust
let cut = text.len().saturating_sub(204_800);      // 字节偏移
let boundary = text[cut..].find('\n')...;          // 若 cut 落在多字节字符中间 → panic
```

中文日志（本项目日志大量中文）几乎必然触发。release 配置是 `panic = "abort"`（[Cargo.toml#L69](../src-tauri/Cargo.toml#L69)），**整个应用会直接退出**。

**建议**：

```rust
let mut cut = text.len().saturating_sub(204_800);
while cut < text.len() && !text.is_char_boundary(cut) { cut += 1; }
```

或按行反向累加字节数，天然安全。

### 3.9 P1｜AI 安全策略与配置项大量"不可达"

| 配置项 | 后端 | 前端 UI | 结果 |
|---|---|---|---|
| `ai_policy` (`Strict/Recommended/Permissive`) | 有 | 无 | 永远 `Inherit` |
| `settings.default_policy` | 有 | 无 | **从未被读取** → Inherit 实际恒为 Recommended |
| `ai_blocklist_regexes` | 有 | 无 | 永远空 |

| `mcp_host/port/autostart` | 有 | 无 | 改不了端口 |
| `idle_detach_minutes` | 有字段 | 无 | AI attach 永不超时 |
| 公钥认证 / Agent | 有/无 | 无 | 不可达 |

**位置**：[security.rs#L25-L34](../src-tauri/src/security.rs#L25-L34)、[session.rs#L410-L427](../src-tauri/src/session.rs#L410-L427)、[session.rs#L136](../src-tauri/src/session.rs#L136)

其中 `AIPolicyOverride::Inherit` 的 `From` 实现直接返回 `Recommended`，注释写着 "caller should substitute global setting"，但**没有任何 caller 做这件事**——这是一个典型的"注释承诺了、代码没兑现"。

**建议**：
1. `SessionHandle::new` 增加 `default_policy: SecurityPolicy` 参数，`Inherit` 真正继承全局；
2. 增加**设置面板**（这是目前最大的 UI 缺口）：全局策略、MCP 端口、日志开关与保留期、默认终端字号、主题；
3. 会话编辑对话框补齐：认证方式切换（密码/私钥/Agent）、AI 策略、日志开关、keepalive；
4. `connect_handle` 用 `client::Config { keepalive_interval: Some(Duration) , ..Default::default() }`；
5. 启动时对 `auto_connect == true` 的会话自动连接（放在 `restore_sessions` 后）。

### 3.10 P1｜敏感数据通过 IPC 全量传到 WebView

**位置**：[commands.rs#L78-L95](../src-tauri/src/commands.rs#L78-L95)

`list_sessions` 返回 `SessionConfig` 全量克隆，`AuthConfig::Password { password_ref }` 里就是**明文密码**。前端 `flatten()` 只取几个字段，但密码已经进入 WebView 内存，并可被任何 XSS/DevTools 读取。

同时 `AuthConfig` 的字段名叫 `password_ref`（暗示是引用/句柄），实际存的是明文——命名误导。

**建议**：
1. 新增 `SessionListItem` 视图模型，`#[serde(skip)]` 掉 `auth`，需要编辑时单独 `get_session_secret`（仅当前窗口、一次一份）；
2. 重命名 `password_ref` → `password`（或 `secret`），消除误导；
3. 长期：密码存 Windows Credential Manager / DPAPI，配置文件只留引用 ID。

### 3.11 P1｜`cancel_transfer` 无法真正取消

**位置**：[commands.rs#L1184-L1207](../src-tauri/src/commands.rs#L1184-L1207)

传输任务只是 `DashMap` 里的一条记录，没有任何取消标志；`sftp_upload` 的循环也不检查。点"取消"的实际效果是**删除进度条**并 `rm -f` 远端文件，而后台仍在继续写——下次 list 会出现文件。

**建议**：`TransferJob` 增加 `cancel: Arc<AtomicBool>`，循环每块检查；取消后等待当前块完成再清理 `.part` 文件。

### 3.12 P1｜前端轮询过密，事件通道是历史遗留

**位置**：[App.jsx#L101-L125](../src/App.jsx#L101-L125)、[session.rs#L223-L274](../src-tauri/src/session.rs#L223-L274)

- 主窗口：monitor 每 1s、AI 事件每 2s、SFTP 窗口每 1s 拉 `list_transfers` 全量；
- 后端同时用 `app.emit` **和** `win.eval(...)` 双通道推送终端数据，前端只监听一处——这套 `eval` 注入是为了解决早期 React 未挂载的竞态；
- `App.jsx` 里自杀式 8 秒轮询兜底（[App.jsx#L85-L91](../src/App.jsx#L85-L91)）说明事件通道并不可靠。

**建议**：
1. 删除 `emit_event` 里的 `win.eval` 分支，统一用 `app.emit`；前端在 `useEffect` 首次挂载后主动 `list_sessions()` 拉一次兜底，替代 8 秒轮询；
2. 监控快照改为后端**推送**（`monitor-update` 事件，1s/次），前端只做渲染；
3. 传输进度改为 `transfer-progress` 事件推送（节流 200ms），去掉 1s 全量轮询；
4. 三条轮询全部去掉后，空闲态 CPU 与 IPC 流量会明显下降。

### 3.13 P2｜其余代码质量问题（按文件归类）

**session.rs**
- `eprintln!` 日志（[L513](../src-tauri/src/session.rs#L513)、L552、L560、L568、L573、L578、L583、L271-272）散落在热路径，release 下仍有格式化开销，应统一到 `tracing::debug!`。
- `end_reason` 初值 `"连接结束"` 永不被读到（编译器已警告）。
- `latency_ms` 恒 `None`，UI 无延迟展示。
- `pending_human_input` 上限 512 字节且超限丢**最旧**数据——用户粘贴一段长命令时会被截断且无提示。

**commands.rs**
- `job_start` 在持有 `state.inner.read()` 时遍历清理 DashMap，逻辑正确但持读锁时间偏长，建议缩小作用域。
- `sftp_download_dir_to_local` 对每个文件单独 `sftp_download`（内部再 `exec`），无并发、无字节级进度、失败静默跳过。
- `open_in_explorer` 的 macOS 分支 `if p.is_dir() { "-R" } else { "-R" }` 恒等，属笔误。
- `open_sftp_window` 在 `std::thread::spawn` 里 build 窗口，成功后没有把实际 label 回写（label 是拼出来的，尚可），但**窗口被用户点 X 关闭后 state 里的 `sftp_windows` 不会清理**，下次打开会走到 `get_webview_window` 返回 None 再重建，不影响功能但有轻微泄漏。建议监听 `WindowEvent::Destroyed`。
- 未使用的 `TransferStatus::Paused`。

**logging.rs / sftp_log.rs**
- `global_log_path()`、`exe_dir()`、`EventRingBuffer::drain()` 均为死代码（编译告警已列出）。
- `sftp_log::log` 每条都 `open` 文件，高频 LIST 时有 IO 放大；`log_result` 未被使用。
- `list_logs` 用 `_{host}_{port}.log` 后缀匹配，同一主机的多个会话日志混在一组。

**state.rs**
- `restore_sessions` 注释仍写"密码以明文存储，MVP 限制"，与实际的 AES-GCM 加密不符，会误导后续维护者。
- 每次配置变更都 `load_store()`（解密+反序列化）再 `save_store()`（序列化+加密+整文件写），会话多时是 O(n) 写放大；可加内存缓存 + 脏标记 + 防抖落盘。

**前端**
- `SftpWindow.jsx`：`useEffect(() => loadLocal(localPath), [localPath])` 与 `loadLocal()` 内部 `setLocalPath()` 组合会导致**进入目录时请求两次**；远端同理。
- `SftpWindow.jsx` 未在依赖数组中包含 `session`，`session` 就绪前后状态可能读到旧值。
- `Sidebar.jsx` 右键"删除会话"与悬浮删除按钮**都没有二次确认**（[Sidebar.jsx#L75](../src/components/Sidebar.jsx#L75)），误删即丢配置。
- `Terminal.jsx` 新增的 `buildSelectionHtml` 用魔法值 `0x2000000` / `0x1000000` 判断颜色模式，应改用 xterm 的 `cell.isFgRGB()` / `isFgPalette()`。
- `BottomPanel.jsx` 里 `spark()`、`toPoints()`、`toPointsNet()` 三份几乎相同的折线生成逻辑；1072 行单文件建议拆分。
- 大量内联 `style` 对象每次渲染重建，建议抽到常量或 CSS 变量。
- `index.css` 与内联样式混用，主题色通过 CSS 变量（好），但仍有 `#DC2626`、`#10B981` 等硬编码色值散落。

**工程化**
- 无任何单元测试。最值得测的纯函数：`security::check`、`monitor::parse_sample`、`logging::strip_ansi`、`session::exec_collect` 的退出码解析、`shell_quote`。
- `Cargo.toml` 中 `portable-pty`、`tokio-util` 未使用。
- `tauri.conf.json` 的 `bundle.targets` 只有 `nsis`；`csp: null`。
- 存在两份 `sftp.html`（根目录与 `public/`），实际路由走的是 `index.html#/sftp`，模板文件冗余。

### 4.2 终端体验

## 七、结论

代码的"完成度"在功能列表上很高，但在**架构一致性**上偏低：

- 同一个能力被两套实现覆盖（SFTP 标签页 + 独立窗口）；
- 同一份数据被两种机制推送（`emit` + `eval`）；
- 同一个配置被三层各存一份（localStorage / `data.0` / DashMap）；
- 大量后端能力没有前端入口，前端又在轮询后端已有的状态。

建议接下来**不要继续加功能点**，而是先做一次"收敛"：把 MCP 做成真正可用的（这是差异化卖点），把 SFTP 换成协议实现（这是性能天花板），把状态模型理顺（这是隐蔽 bug 的源头）。这三件事做完，产品的下限会显著抬高，后续加功能才不会再被现有缺陷拖住。
