## 1. 审计范围与方法

覆盖 `src-tauri/src` 全部 Rust 模块（会话、SFTP、监控、MCP、审批、安全策略、状态与日志）与 `src` 前端，抽查 `vendor/` 本地修补依赖。审计分两轮独立进行：

- 安全审计：按攻击面逐个读实现，只记录能在代码中指认的问题，推测性结论标注待验证
- 质量审查：正确性、并发、可维护性、测试覆盖、性能

未做动态渗透、未对真实主机复现利用；下文「确认」指代码路径成立，不等于已在运行环境复现。

## 4. P0 修复方案（V1.0.0.12）

### P0-1 状态变更类 MCP 工具授权收紧

**问题**

`mcp_tools.rs` 的 dispatch 中，`session_create`、`session_connect`、`session_disconnect`、`forward_add`、`forward_stop` 的函数签名不接收 `client`，无法校验 attach_token，仅凭全局 Bearer 凭据即可调用：

- `session_create` 可向任意外部主机发起 SSH 连接，把本机充当跳板，并让密码进入 Windows 凭据库
- `forward_add` 的 `listen_host` 无任何校验，`remote` 类型默认监听 `0.0.0.0`，可将本机任意端口暴露到局域网，且会写入会话配置持久化

**触发路径**

`POST /mcp` → `tools/call` → dispatch → `session_create{host,username,password,connect:true}` 或 `forward_add{listen_port,dest_host,dest_port}`。

**修复方案**

1. dispatch 向上述 5 个函数传入 `client`，统一在函数入口校验：
   - `session_connect`/`session_disconnect`：要求该会话的 writer attach_token
   - `forward_add`/`forward_stop`：要求绑定同一会话的 writer attach_token
   - `session_create`：无既有会话可绑定，改为调用 `approval::request` 弹人工确认
2. `forward_add` 的 `listen_host` 白名单限定 `127.0.0.1` 与 `::1`；其他取值必须走人工审批
3. `remote` 类型 `listen_host` 默认值由 `0.0.0.0` 改为 `127.0.0.1`
4. 审批被拒或超时：不建立连接、不写配置、不产生持久化副作用

**验收标准**

- 无 attach_token 调用 5 个工具均返回 `FORBIDDEN`，且无任何副作用
- `listen_host=0.0.0.0` 未审批时被拒，审批通过后配置中可见且重启后仍生效
- 审批超时后 `forward_list` 与配置文件均无新增条目
- 现有 `session_exec`/`sftp_*` 审批链路测试全部通过

**待决策**：`session_create` 是「加审批保留」还是「直接移除」。移除攻击面最小，但 AI 将无法自主新建会话。

### P0-2 只读白名单参数面加固

**问题**

`readonly_command_allowed` 的路径边界校验仅在条目自身声明了路径时执行。内置清单中 `dig`、`curl -I`、`ls`、`stat`、`wc`、`readlink`、`du`、`lsof` 均为无路径条目，因此可接受任意绝对路径参数；`DANGEROUS_ARGS` 又未覆盖 `dig -f`、`curl -D/-c`、`sar -o`，导致只读诊断模式下可读写任意文件。

**修复方案**

1. 无路径声明的条目，凡参数中出现绝对路径或含路径分隔符的值，一律拒绝
2. 需要访问固定路径的命令改为显式声明目录前缀（如 `cat /proc/`、`cat /etc/os-release`）
3. `DANGEROUS_ARGS` 补齐：
   - `dig`：`-f`、`--file`
   - `curl`：`-D`、`--dump-header`、`-c`、`--cookie-jar`、`--trace`、`--trace-ascii`
   - `sar`：`-o`、`-f`
4. 参数匹配前统一归一化 `--key=value` 形式
5. `has_unsafe_path_syntax` 增加拒绝 `*`、`[`、`?` 通配
6. root 登录会话沿用既有收敛规则，不因条目变化放宽

**验收标准**

- 新增表驱动测试，下列输入全部拒绝：`dig -f /etc/shadow`、`curl -I -D .ssh/authorized_keys http://x`、`sar -o /tmp/x 1 1`、`ls /root`、`cat /etc/shadow`
- 合法只读命令（`systemctl status nginx`、`docker ps`、`ip addr show`）仍放行
- 现有白名单测试无回归

**兼容性影响**：老配置中的宽条目升级后可能失效，需在「设置 → AI 安全」增加一次升级提示（见第 8 节）。

### P0-3 sudo 口令泄漏

**问题**

`exec_collect_root` 在 `sudo -S -p ''` 后固定等待 150ms 写入口令。当 sudo 凭据仍在缓存有效期时，`sudo -S` 不读取 stdin，口令行成为后续 `sh -lc '<cmd>'` 的标准输入；命令若读取 stdin（`cat`、`mysql`、`ssh-add` 等），口令会进入 stdout、回传 AI 并写入 AI 回显日志，而现有脱敏不匹配裸口令。

**修复方案**

1. 先执行 `sudo -n true` 探测：命中缓存则不再写入口令
2. 需要口令时再执行 `sudo -S -p ''`，写入后立即发送 `ch.eof()`，避免口令残留在命令 stdin
3. 纵深防御：会话级动态脱敏，把当前会话 sudo 口令注册进 `StreamRedactor`，日志与 AI 回显中出现时替换为 `***`
4. 失败重试次数保持 1 次，避免口令反复写入

**验收标准**

- 单测覆盖「缓存有效场景下 stdin 为空」
- 动态脱敏单测：口令出现在输出中被替换
- 真实 sudo 环境手工验证一次：连续两条 root 命令，第二条为读 stdin 的命令，输出中不出现口令

## 6. P2 修复方案（V1.0.0.13）

**P2-1 连接超时竞态**
超时分支复位 `worker_running` 并设置取消标志；「已在连接中」返回 `Err` 而非 `Ok(())`。验收：模拟建连超时后再次重连，状态与实际连接一致。

**P2-2 日志热路径**
日志写入改为有界异步队列批量落盘；`log-appended` 事件至少 1s 节流，或改为面板可见时轮询文件大小。验收：`cat` 10MB 文件期间终端输入无明显延迟，IPC 调用数量下降一个数量级。

**P2-3 转发表键**
`remote_targets` 键改为 `(session_id, port)`；所有退出路径统一 `forwards.remove`。验收：两个会话同端口转发互不影响；失败后规则可重新启用。

**P2-4 SFTP 超时**
读写与 `sftp::connect` 包 `tokio::time::timeout`；`cancel()` 加兜底超时并强制置为 Error。验收：黑洞网络下取消可在超时内返回。

**P2-5 审批消费时机**
`consume_approved` 移到真正下发命令前；Block 或执行失败路径回滚为 Approved。验收：被判 Block 后审批仍可用于下一次正常请求。

**P2-6 锁语义统一**
明确规则：普通配置字段用 `RwLock`；DashMap 等并发容器不再叠加外层锁。验收：`cargo test` 全通过，监控写锁下命令延迟无明显抖动。

**P2-7 测试与 CI**
补 `forward.rs` 单元测试、断点续传集成测试（offset 复用、`.part` 一致性）；CI 增加 `cargo clippy -- -D warnings`。验收：新增测试在 CI 常态执行，转发与续传不再是零覆盖。

## 7. 已验证未发现可利用问题的部分

- MCP 令牌：32 字节 CSPRNG 生成、加盐 SHA-256 存储、常量时间比较、只存哈希、与 client/session 绑定、单次消费、30s 过期
- stdio 模式：仅转发，强制 loopback，禁止内嵌凭证
- 配置与秘密：AES-256-GCM + DPAPI 主密钥，口令与私钥存 Windows 凭据管理器，DTO 不返回秘密
- CSP：无 `unsafe-inline` 脚本，`connect-src` 仅 self 与 ipc；前端无 `eval`、无 `dangerouslySetInnerHTML`
- 命令执行：sudo 命令经单引号转义，argv 不可注入；监控与转发使用固定脚本
- 路径：本地目录下载做 `Component::Normal` 校验，`..` 与 UNC 穿越被拦截，覆盖前有冲突检测
- 依赖：`vendor/pageant` 随机 cookie 与长度校验完整，`vendor/russh-sftp` 未见 `unsafe` 或越界读写

## 9. 决策记录

三项待决策已在 V1.0.0.12 实施前确认：

1. `session_create`：保留，改为调用人工审批（首次返回 `WAIT_CONFIRM`，确认后带 `confirmation_id` 重试）。
2. 设置页：增加一次性提示，说明本次白名单收紧范围，可关闭且关闭后不再出现。
3. 主机密钥指纹确认：只对 AI 建立的会话与 AI 发起的连接强制；AI 在指纹未确认时返回 `HOST_KEY_CONFIRM_REQUIRED`，需用户在界面手动连接一次，人类手动建连行为不变。

实施时对 P0-2 做了一处调整：原方案要求「无路径条目一律拒绝绝对路径」，实测会误伤 `df -h /var`、`ls /tmp` 这类日常诊断。最终实现为：

- 读取类命令（如 `cat`）的绝对路径必须由白名单条目显式声明；
- `ls`、`stat`、`du`、`df`、`wc`、`readlink`、`lsof`、`findmnt`、`blkid` 等只输出元数据的命令允许普通绝对路径；
- 无论哪种命令，`/root`、`/etc/shadow`、`/etc/sudoers`、`.ssh`、私钥文件名、`/proc/*/environ` 等敏感路径一律拒绝。

## 10. 边界说明

本方案基于静态审计，未在真实攻击环境验证利用链。P0-1 与 P0-2 的验收用例为代码级断言，真实主机上的行为仍需在受控环境复验一次。修复完成后建议重新跑一次微步沙箱与全量门禁，确认没有引入新的误报行为。
