Chena-Shell — 产品需求文档

桌面应用 · 开发者工具 · 同时面向人类用户和 AI agent

1. 背景与问题

开发者日常需要 SSH 到多台主机执行命令、传输文件。现有的 SSH 客户端（Xshell、PuTTY、Windows Terminal）都只服务人类用户，无法被 AI agent 以统一方式调用。与此同时，已有 AI SSH 工具（如当前 TRAE 的 persistent-ssh-terminal）虽然具备命令执行能力，但 没有图形化界面、文件传输靠独立工具、AI 做了什么人类看不见——用户完全失去对远程会话的可见性和控制权。

Chena-Shell 的核心产品判断：把 SSH 客户端做成一个 AI 友好的"双入口"产品——人类用户打开 GUI 直接操作，AI agent 通过统一接口调用同一套底层能力。两边的活动在同一个界面里可见、可控、可追溯。

2. 产品契约

项决策

  • 密钥管理（集成 ssh-agent）
  • 端口转发管理（可视化增删改查）

  • 命令历史搜索
  • 资源监控历史回溯（5 分钟 → 1 小时 → 24 小时）

  • X11 图形转发
  • 团队会话共享/协作
  • SFTP ACL 权限管理
  • 插件市场

4. 技术栈选型（已更新，解决臃肿问题）

为什么不选 Electron

Electron 把 Chromium 浏览器引擎（~130 MB）和 Node.js（~30 MB）一起打包，最终安装包 150–250 MB，冷启动 200–500 ms，运行内存 150–300 MB。Chena-Shell 作为一个终端 + 文件传输工具，完全不需要浏览器渲染能力——Electron 是典型的"杀鸡用牛刀"。

最终推荐

首选 Tauri v2：体积最小（3–10 MB，Electron 的 1/20～1/50）、启动最快（< 50 ms）、内存最低（50–80 MB）、性能最好。Rust 生态里 SSH 能力完整，UI 层用 Svelte/React 开发体验好。Tauri 复用系统 WebView2（Windows 10+ 自带，Edge 内置），不额外打包浏览器引擎。

次选 Wails v2：如果团队更熟 Go。Go 标准库自带 SSH 实现不依赖 libssh2，体积一样 3–10 MB，开发比 Rust 友好。

备选 C# WinUI 3：如果纯 Windows 生态、.NET 团队、需要最高开发效率。不跨平台但原生性能好，15–25 MB 也远好于 Electron。

功能详情

点击 prototype 中的元素会跳转/聚焦到对应的功能章节

FR-01

会话管理器

目的：让用户持久化保存多台 SSH 主机的连接配置，快速连接/断开，并标记哪些会话当前有 AI 接入。

布局

左侧固定 200px 导航栏，从上到下依次：+ 新建按钮、搜索框、会话列表。每条会话显示连接状态小圆点、名称、补充信息（远端标识或"已断开"），有 AI 接入时右上角显示紫色 "AI" 小标签。

触发与处理规则

  • 新建：点 + 弹出会话配置对话框，四个 tab — 基础（主机/端口/用户）、认证（密码/私钥/ssh-agent）、高级（keepalive/shell/自动重连）、AI 权限（是否允许 AI 接入 + 文件传输级别 + 自定义拦截正则）。保存后连接。
  • 编辑：右键会话项 → 编辑，打开同一个对话框。
  • 删除：右键 → 删除，弹出确认框 "确定删除会话 [名称]？该会话的命令历史和 SFTP 书签将一并删除"。
  • 连接/断开：单击会话名连接；右键或点标签页关闭按钮断开。断线后圆点变灰，自动重连开启时自动重试。
  • 导入/导出：支持从 Xshell、PuTTY、OpenSSH config 导入会话；导出为加密 JSON（AES-256），避免密码/私钥泄露。

字段规则

字段类型必填默认验证
会话名称字符串是—唯一；≤ 50 字符；不能含 \/:*?"<>|
主机字符串是—合法 hostname 或 IPv4
端口整数是221–65535
用户名字符串是当前 OS 用户非空
认证方式枚举是密码+私钥密码/私钥/ssh-agent/仅密码/仅私钥
密码字符串否—本地 AES-256 加密存储
AI 可接入布尔是是否则 AI 接口无法在该会话执行任何操作

异常

  • 导入文件损坏：提示 "文件不是有效的 Chena-Shell 会话文件或密钥不匹配"。
  • 删除 AI 正在使用的会话：阻断删除操作，提示 "当前有 AI 在会话 [名称] 上执行操作，无法删除"。
  • 会话名称重名：保存时提示并高亮名称字段。
FR-02

终端连接与生命周期

目的：让用户和 AI agent 都能在同一个 SSH Session 上交互执行 shell 命令，同时通过多标签页管理多台主机。

布局

主区域。上方是标签页栏（显示活跃主机名 + AI 小圆点 + 关闭按钮），下方是终端模拟器区域（深色背景，等宽字体，光标闪烁）。连接状态异常时终端顶部出现横幅（红色=断开、蓝色=连接中、紫色=AI 活动中）。

处理规则

  • 连接成功：标签页的状态圆点变绿；终端输出欢迎信息（Last login 等）；AI 活动横幅（如果有 AI 在使用）出现。
  • 连接中：终端顶部显示 "正在连接 [主机]…" 蓝色横幅，带 spinner；超时 15 秒后显示失败横幅。
  • 断线：标签页圆点变灰；终端输出红色提示 "连接已断开 — 将在 5 秒后自动重连"；用户点"立即重连"按钮可加速。自动重连超过最大次数（默认 5）后停止，需用户手动重试。
  • 多标签页：每个标签页是独立的 SSH Session，可以指向同一台主机也可以不同。AI 调用默认在最近活跃的标签页执行，AI 接口可以指定 session ID。
  • PTY 写权限：由会话的 attach_state 状态决定（FR-08），详见 共享规则。简化理解：默认 human_only = 只有人类能写；AI 调用 session.attach() 后变成 ai_attached = AI 能写、人类输入缓冲；AI detach() 后自动回到 human_only。

状态转换

当前状态触发下一个状态用户可见
未连接点"连接"连接中蓝色横幅
连接中握手成功已连接标签页变绿
连接中握手失败/超时错误红色横幅 + "重试"按钮
已连接远端断开/网络中断重连中红色横幅 + 倒计时
重连中重连成功已连接标签页恢复绿点
重连中超过最大次数错误停止自动重连
错误用户手动重试连接中—

异常

  • AI 试图连接一个"AI 可接入=否"的会话：接口返回 403，会话无任何视觉变化。
  • 会话被用户关闭时 AI 仍在执行：后台线程收到 EOF，AI 接口返回 "Session closed by user"；AI 活动面板标记"被用户中断"。
  • 同一 AI 请求同时打到多标签页：接口按 session_id 路由；未指定 session_id 时走"最近活跃"策略。
FR-03

终端模拟器（含全屏 TUI）

目的：在 GUI 里提供与原生终端完全兼容的 shell 交互体验，包括 Vim、top、nmtui、htop 等全屏 TUI 程序。

处理规则

  • Shell 交互：PTY 模式运行，所有 ANSI/VT100 转义序列正确渲染；窗口 resize 时自动 SIGWINCH。
  • 全屏 TUI：不需要特殊处理——因为用 PTY，vim/top/nmtui 等程序原生就工作。[Assumption, TBD] 支持鼠标滚轮（scrollback）和终端内鼠标事件（如 vim 可视模式的鼠标选择）。
  • 复制粘贴：选中 → 复制（Ctrl+C 或右键菜单）；粘贴（Ctrl+V 或右键粘贴）。粘贴多行时自动加换行。
  • 滚动缓冲：默认 5000 行，可在设置里改。独立于远端的 screen/tmux 缓冲。
  • 快捷键：Ctrl+C/D/L/U 等控制字符正常透传到 shell，不被 GUI 拦截。

AI 命令的终端内标记

AI 通过 PTY 发出的输入行，在终端中以 紫色高亮 + 行首 "AI " 小徽标 显示。这个标记是渲染层的元数据（不是真实 PTY 内容），不会被终端程序读到。这样用户一眼就能区分哪些命令是自己打的、哪些是 AI 发的。

回显智能高亮（P0）

PTY 输出经过解析层后，对常见输出模式进行语义染色。这是渲染层的后处理，不修改真实 PTY 字节流。

配置文件 cat 输出 检测到 { } / 分号 / 等号 / 注释 # 括号=红、关键字=紫、字符串=绿、数字=粉、注释=灰斜体（类 nginx/CONF 语法）
ls -l -rwxr-xr-x user group size date name 权限 x=绿、w=橙、r=默认；可执行文件名=绿；目录=蓝加粗；符号链接=青
通用数值 行内独立数字、IP 地址、端口、百分号 数值=粉、IP=蓝、端口=紫加粗、百分比>85%=红

识别策略

  • 轻量启发式（P0）：每行 PTY 输出进入渲染层前，用规则正则 + 简单上下文匹配做识别。不调用外部语法高亮引擎，延迟目标 < 1ms/行。
  • 语言检测（P1）：当连续多行输出包含 { } ; = 或 # // /* 时，自动检测为对应语言（nginx/CONF/bash/Python/JSON 等），切换到语言特定的 token 表。
  • AI 命令上下文：AI attach 期间输出的 shell 命令行自动走 shell token 化，人类手动输入的命令也走相同规则。
  • 可关闭：设置里"终端 → 回显语法高亮"开关可关闭，关闭后终端只渲染原始 PTY 字节（带 ANSI 颜色），不做后处理。

为什么 P0 就做

  • AI 排查场景里，systemd 红 active failed、端口冲突、日志 error 行这些关键信息需要"跳出来"，不然用户扫一眼终端找不到 AI 到底发现了什么
  • 人类自己操作时也受益 — ls -l 的可执行文件一眼绿、ss 输出的 LISTEN 端口一眼紫
  • 实现成本可控：规则正则表 + token 颜色映射，不依赖 tree-sitter 等重型引擎
FR-04

SFTP 文件传输

目的：让用户无需另开工具就能在 Chena-Shell 里浏览、上传、下载远端文件；同时暴露给 AI 做程序化的文件操作。

布局

底部可折叠面板（高度可拖拽，默认 240px），左侧 tab 切换 SFTP / AI 活动 / 端口转发。SFTP 面板左右双栏：左侧本地、右侧远端，都有路径栏和文件列表。

处理规则

  • 浏览：点击目录进入；支持路径栏直接跳转；显示文件名、大小、修改时间。
  • 拖拽传输：本地 → 远端 拖拽文件/目录触发上传；远端 → 本地 触发下载。拖拽时进度条悬浮显示。
  • 右键菜单：上传、下载、重命名、删除、新建目录、复制路径。
  • 进度与并发：单个传输任务显示进度（字节+百分比+速度）；最多 3 个并发任务，超出排队。完成后通知气泡。
  • 断点续传：P0 ✓ 传输过程中断线重连后自动从断点恢复（记录已传字节数，用 SFTP check-resume 扩展查远端文件大小）；传输队列持久化到本地 JSON，应用重启后自动恢复未完成任务。
  • 覆盖冲突：目标存在时弹窗选择"覆盖 / 跳过 / 重命名副本 / 全部覆盖 / 全部跳过"。AI 发起的传输冲突：AI 不能决定，Chena-Shell 弹窗让用户选，30 秒超时默认跳过重试不覆盖。
  • AI 接口：暴露以下能力给 AI：listdir、stat、upload(local_path, remote_path)、download(remote_path, local_path)、delete、rename、mkdir。AI 发起的传输同样在 SFTP 面板有进度显示。

异常

  • 会话未连接时 SFTP 面板显示"无活跃会话"空状态，禁用所有操作按钮。
  • AI 在"AI 文件传输权限=仅下载"的会话上调用 upload：接口返回 403，SFTP 面板弹出提示"当前会话配置不允许 AI 上传"。
  • 磁盘空间不足/远端配额超限：进度条停住，弹窗显示具体错误。

AI 接口暴露

暴露形式（TBD-01 已决：只做 MCP Server）

P0 只暴露 MCP Server，砍掉 CLI 和 WebSocket（CLI 和 WebSocket 留作未来场景，等实际需求出现再加）。

层级内容命中后行为

FR-08

AI attach / detach — 访客模式

目的：让外部 AI agent（如 Trae）通过接口临时"接入"一个人类已经手动连接好的会话，在同一个 PTY 里排查问题、执行命令，然后安全退出。AI 永远是访客，会话始终归人类所有。这是 Chena-Shell 作为"被 AI 调用的 SSH 服务"的核心能力。

典型场景（主场景）

  1. 你在 Chena-Shell 里手动连好 prod-web-02，正在操作中 —— nginx 502，自己搞不定
  2. 切到 Trae 客户端（另一个应用），新建任务："帮我排查 prod-web-02 的 nginx 502" —— Trae 通过 Chena-Shell 暴露的 MCP 接口调用 session.attach("prod-web-02", reason="nginx 502 排查")
  3. Chena-Shell 里你正在看的 prod-web-02 终端实时显示 Trae 的每一步操作（紫色标记 + "AI " 徽标），你全程看
  4. Trae 跑完 journalctl、systemctl status nginx、tail -f error.log，定位到配置语法错误，调用 session.detach(reason="搞定了，修复了 nginx.conf 里的端口号")
  5. Chena-Shell 自动恢复到人类独占状态，你在同一个终端里继续手动操作 —— 整个过程你没有离开过这个会话

Session AI 状态（三态，足够）

AI attach 流程（接口侧）

  1. AI 调用 session.attach(session_id, reason, mode="attached")
  2. Chena-Shell 检查：会话是否存在 → 是否已连接 → 会话级 AI 权限是否允许 → 当前是否有其他 AI attach（同一时刻只能一个 AI attach）
  3. 检查通过 → 状态切为 ai_attached（或请求的 mode）；返回 attach_token（后续 exec 调用需要带上，防止伪造）
  4. 检查失败 → 返回 403/404/409；AI 活动面板不产生任何条目

AI 会话期间的规则

  • AI 操作可见性：AI 发出的每条命令在终端中以紫色 + "AI " 徽标显示（同现有设计）；AI 活动面板实时更新；标签页出现 🤖 紫色圆点。
  • 人类输入缓冲：人类在 AI attach 期间打的字符，被缓冲在一个 512 字节的 FIFO 队列里。AI detach 后，缓冲内容以 每个字符间隔 5ms 的速度回放进 PTY（避免 shell 来不及处理）。队列溢出 → 丢弃最早的 128 字节并在 AI 活动面板提示。
  • AI 安全检查：attach 之后，AI 的每条 exec() 仍然走 FR-07 的安全拦截清单。attach 是"入场券"，不是"通行证"。
  • 同一个会话只允许一个 AI attach：如果 session_id 已经是 ai_attached 状态，另一个 AI 再调用 attach → 返回 409 "Another AI is currently attached"。
  • AI attach token：attach 成功后 Chena-Shell 返回一个 token，后续 exec/pty_write/detach 调用必须带上这个 token。token 在 detach 或会话关闭后失效。防止非授权 AI 冒充已 attach 的 AI。
  • AI detach：AI 完成后调用 session.detach(session_id, reason)，状态自动切回 human_only，缓冲的人类输入开始回放。detach 不需要任何确认，是 AI 主动结束的标准流程。

人类可见的 UI 反馈

  • 终端顶部横幅（淡紫色）：AI attach 时出现 "🤖 [AI 名称，如 Trae] 正在排查 [会话名] — 原因：[reason]"；detach 时变为绿色 "🤖 [AI 名称] 已退出 — 原因：[reason]"，3 秒后淡出。
  • 标签页：🤖 紫色圆点表示有 AI attach；右侧出现小按钮 "✕ 踢出 AI"（只在 ai_attached 状态显示），人类可以随时点这个强制终止 AI 会话（等价于 detach，AI 接口收到 "Forced detach by user"）。
  • AI 活动面板顶部："当前 [会话名] 状态：AI attach 中 · 等待 AI 退出后回放输入"；AI 事件列表里出现 attach / detach 两条入口/退出记录。
  • 终端输入区：ai_attached 状态下，输入框变灰 + 小字提示 "AI 排查中 — 你的输入将在 AI 退出后执行"。shared 状态下输入框正常可用 + 小字提示 "共享模式 — 双方都能向终端写入"。

与 AI 接口的完整交互示例（伪代码）

// Trae agent 视角

// 1. 列出 Chena-Shell 里已连接的会话
sessions = chenaShell.session.list({ connected: true })
// => [{ session_id: "abc-123", name: "prod-web-02", host: "10.0.0.50", ai_allowed: true, state: "connected" }]

// 2. attach 到目标会话
attach_result = chenaShell.session.attach(
  session_id: "abc-123",
  reason: "nginx 502 排查",
  mode: "attached"
)
// => { attach_token: "tk_xyz789", current_prompt: "root@prod-web:/var/log#" }

// 3. 在 PTY 里逐条执行命令（终端里每条都紫色显示）
chenaShell.session.exec(session_id: "abc-123", attach_token: "tk_xyz789", command: "systemctl status nginx --no-pager")
chenaShell.session.exec(session_id: "abc-123", attach_token: "tk_xyz789", command: "journalctl -u nginx -n 50 --no-pager")
chenaShell.session.exec(session_id: "abc-123", attach_token: "tk_xyz789", command: "cat /etc/nginx/sites-enabled/default")
// ... 定位到 server 块里的 listen 8080 写错了应该是 80 ...

// 4. 修复
chenaShell.session.exec(session_id: "abc-123", attach_token: "tk_xyz789", command: "sed -i 's/listen 8080/listen 80/' /etc/nginx/sites-enabled/default")
chenaShell.session.exec(session_id: "abc-123", attach_token: "tk_xyz789", command: "nginx -t && systemctl restart nginx")

// 5. 退出，把会话还给人类
chenaShell.session.detach(session_id: "abc-123", attach_token: "tk_xyz789", reason: "搞定了，nginx.conf 里 listen 端口写错了，已修复")

异常

  • AI 在 attach 期间会话断开重连：Chena-Shell 自动重连 PTY，AI 的 attach_token 仍然有效，exec 调用继续走；重连失败超过最大次数 → attach 自动失效，返回 503 给 AI。
  • AI 持有 attach_token 但人类关闭了该标签页：AI 接口收到 "Session UI closed"（PTY 其实断了），Chena-Shell 标记会话为 error 状态。AI 可以选择重新 attach 或放弃。
  • 人类点"踢出 AI"：AI 正在执行的命令在 PTY 层面被终止（发送 SIGHUP），AI 接口收到 "Forced detach by user"，attach_token 立即失效。
  • AI attach 后长时间没有任何 exec（默认 10 分钟）：Chena-Shell 自动 detach，避免 AI 意外挂住会话。AI 收到 "Auto-detached due to inactivity"。
  • 两个 AI 同时调用 attach：第二个收到 409，返回正在 attach 的 AI 名称和 attach 起始时间，让调用方选择是等待还是放弃。

采样策略（控制远端开销）

  • 采样间隔：默认 2 秒；用户可在全局设置里改（1 秒 ~ 10 秒）。CPU、内存、网络、负载、TOP 进程共用同一次采样，避免多次命令。磁盘使用率（df）采样频率减半（4 秒一次）——因为磁盘变化慢，省开销。
  • 采集实现：优先用"读文件 + 本地计算"的轻量方式（/proc/*、/sys/*），避免执行 vmstat、top -b -n1 这类有开销的进程。macOS 没有 /proc 时降级到 sysctl + netstat。
  • 开销上限：单会话监控的远端 CPU 占用目标 ≤ 0.5%，内存增量 ≤ 2 MB。采样间隔和采集方式都为这个目标服务。
  • 缓冲窗口：UI 显示最近 5 分钟（150 个点 @ 2 秒）的 sparkline 数据。超过窗口的旧数据丢弃（不做持久化，历史回溯 P1）。

视觉反馈（FinalShell 风格 + 简化）

  • 指标卡片：每个指标一个独立卡片，左上指标名、右上当前值（大号加粗）、中间进度条 + sparkline 图、底部小字详细值。卡片水平排列，总宽度随底部面板宽度自适应。
  • 颜色语义：CPU < 60% 绿、60–85% 黄、> 85% 红；内存 < 70% 绿、70–90% 黄、> 90% 红；磁盘同上。颜色渐变通过 CSS transition 平滑过渡（0.6 秒）。
  • 网络双线：入流量（↓）实线绿色，出流量（↑）虚线红色，在同一个 sparkline 里叠加显示。
  • 状态指示：底部面板最下方有一行小字：采样间隔 · 历史窗口长度 · 当前"正常 / 警告 / 严重"状态 · 是否自动刷新中。
  • 会话切换：切换标签页时，监控面板自动跟随当前活跃的会话；不同会话的监控数据独立采集、独立缓冲、独立显示。

与 AI 的交互

监控面板对 AI 完全透明——AI 不需要、也无法控制采集流程。但监控的数据对 AI 排查有价值：

  • AI attach 到会话后，可以直接在 Chena-Shell UI 上看到实时 CPU/内存/网络曲线，**和人类看的一样**。但 AI 不需要通过接口读监控数据——它自己在 PTY 里跑 top / vmstat 更灵活。
  • [Assumption, TBD] 如果后续 AI 确实需要结构化监控数据，可以加一个只读接口 session.metrics(session_id, since?) 返回当前快照 + 指定时间窗口的历史点。P0 不做。

异常与降级

  • 远端是 **Windows Server**：P0 不支持，监控面板显示 "Windows 监控暂不支持" 空状态；P1 加 WMI / typeperf 采集。
  • 采集命令超时（单次 > 3 秒）：跳过这次采样，保留上一次的数值；连续 3 次超时 → 面板显示 "采集失败 · 检查远端权限" 提示；会话断开重连后自动恢复。
  • TOP 进程采集返回空（系统没有 ps 或被禁）：卡片显示 "-"，不影响其他指标。
  • 单会话被关闭 → 对应采集器立即停止，释放本地缓冲。多会话并行采集开销累加，超过 5 个活跃监控时采集间隔自动调整到 3 秒。
  • AI attach 期间：监控采集**正常继续**，不受 AI 读写 PTY 的影响。采集通过独立的 SFTP/exec 通道实现，和 PTY 会话解耦。

AI 请求生命周期

AI 接口发出 session.exec(session_id, attach_token, command) 后的完整流程：

  1. 收到请求，分配 request_id，状态 = queued
  2. attach_token 验证：token 是否存在、是否匹配该会话、是否已过期 — 任一不通过 → 返回 401，状态 = token_invalid
  3. attach_state 前置检查：当前会话 attach_state 不是 ai_attached 或 shared → 返回 409，状态 = not_attached（人类还没让 AI 进来）
  4. 安全检查：匹配全局黑名单 → 命中则状态 = blocked，AI 活动面板显示拦截
  5. 命中需确认列表 → 状态 = awaiting_user，弹出确认对话框
  6. 用户允许 → 状态 = executing，命令进入 PTY 写队列；终端中显示紫色标记
  7. 命令执行完成 → 状态 = succeeded / failed，AI 活动面板显示结果 + 耗时
  8. 超过 timeout → 状态 = timeout，终端保持原样，AI 接口返回超时

简化理解：没有 attach_token + attach_state 不是 ai_attached → AI 连 exec 的门都碰不到。这是比之前"控制权前置检查"更严格的认证边界。

基于 attach_state 的写权限规则

attach_state人类写入 PTYAI 写入 PTY（需 attach_token）典型场景
human_only立即写入被拒绝（409 not_attached）默认状态，人类正常操作
ai_attached缓冲到 human_input_buffer（512B 上限）立即写入AI 正在排查，人类围观或偶尔插嘴（等 detach 后回放）
shared进入统一 FIFO 写队列进入统一 FIFO 写队列高级场景：AI 跑后台任务、人类随时补命令

规则比之前简单很多。写锁、跨 AI 串行化、复杂状态都砍掉了 — 一个会话同一时刻只允许一个 AI attach，自然就不需要"跨 AI 竞争"的复杂度。

会话级安全 × 全局安全的叠加规则

最终策略 = 会话级配置 ∩ 全局策略，取交集：

全局策略会话级最终效果
允许 AI 接入禁止 AI 接入禁止（会话优先）
默认拦截清单全部放行仍拦截（默认清单不可关闭）
需确认的危险命令全部放行需确认（全局危险命令优先）
AI 文件传输可读写仅下载仅下载（会话优先）

加密与存储

  • 会话配置中的密码、私钥 passphrase 使用 AES-256-GCM 加密，密钥由用户首次设置的主密码通过 Argon2id 派生。
  • 如果用户没有设置主密码 → 降低安全提示 + 操作系统 DPAPI / Keyring 存储。
  • AI 请求历史默认不持久化（仅内存），可在设置里开启磁盘持久化（同样加密）。

✓ 已决 · TBD-03：产品形态与技术栈

Tauri v2 + 本地 exe，不做 Electron，不做云同步。

  • 技术栈：Rust 后端（Tauri v2）+ Web 前端（React + TypeScript）— 体积小（~15MB 安装包 vs Electron ~150MB）、内存占用低（~30MB vs Electron ~200MB）、启动快
